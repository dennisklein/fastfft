\begin{abstract}
\noindent GNU Radio~4 computes FFTs with \code{SimdFFT}, a \code{std::simd} port of PFFFT whose vectors are fixed
at four lanes. We present \code{fastfft}, a single-header radix-8/16 Stockham FFT written against
\code{native\_simd} without ISA intrinsics. On one AVX-512 core it is \FloatVsGrRange{} faster than \code{SimdFFT}
for complex single-precision transforms of size $2^6$--$2^{20}$ and \DoubleVsGrRange{} in double precision, and
between \FloatVsFftwRange{} (float) and \DoubleVsFftwRange{} (double) as fast as FFTW~3.3.10 with AVX-512 codelets.
Inside GNU~Radio~4, a small patch makes the streaming FFT block \GrStreamFloat{} faster (float). C++26 \code{std::simd} in GCC trunk removes the last compiler extension. The code and a harness that repeats all measurements on any Linux host are public.
\end{abstract}

\section{Introduction}
GNU Radio~4 (gr4)~\cite{gr4} is a header-only C++23 rewrite of the GNU Radio signal-processing framework. Its FFT
blocks call \code{gr::algorithm::FFT}, which dispatches to \code{SimdFFT}, a port of PFFFT~\cite{pffft} to
\code{std::experimental::simd}~\cite{ts} via vir-simd~\cite{vir}. \code{SimdFFT} uses
\code{simd<T,\,4>}: four floats or four doubles, whatever the hardware offers. On an AVX-512 machine this leaves
three quarters of each register unused in single precision.

We asked how fast a power-of-two complex FFT can be when written only against \code{native\_simd}, so that the
width follows the compilation target, and whether it can match a tuned library. The answer, \code{fastfft}, is one
\SI{450}{line} header.

\section{Algorithm}\label{sec:alg}
\code{fastfft} is a Stockham autosort FFT~\cite{stockham,vanloan}: every pass reads one buffer and writes the other
in natural order, so no bit-reversal pass is needed. Data are interleaved complex numbers; a vector of $W$ scalars
holds $C=W/2$ complex values (8 floats or 4 doubles per \SI{512}{bit} register).
\begin{enumerate}\setlength\itemsep{0pt}
\item \emph{First pass, radix 8, vectorised over the butterfly index.} With stride 1 the eight inputs of a butterfly
  are $N/8$ apart, so $C$ consecutive butterflies form one vector per input. The eight results of each butterfly
  must be stored contiguously; an in-register $8\times C$ complex transpose (three rounds of two-input zips) does
  this before the store.
\item \emph{Middle passes, radix 16, vectorised over the stride.} Once the stride $s\ge C$, the $C$ lanes of a vector
  are $C$ independent sub-transforms that share a twiddle factor, which is broadcast. A radix-16 butterfly is done as
  $4\times4$ in registers. Each pass reads and writes the data once, so a $2^{20}$ transform takes six passes
  instead of ten for radix 4.
\item \emph{Last pass,} radix 2, 4 or 8, whatever remains.
\end{enumerate}
Complex multiplication by a twiddle $w$ uses tables stored as $(w_r,w_r)$ and $(-w_i,w_i)$ per lane pair, so
$z\cdot w = z\odot\mathbf{w_r} + \mathrm{swap}(z)\odot\mathbf{w_i'}$ costs one multiply, one fused multiply-add and
one in-lane swap. Twiddles are precomputed in double precision. Sizes below 64 use a scalar radix-2 path.

\section{What \texttt{std::simd} could not express}\label{sec:simd}
The kernel uses \code{std::experimental::simd} as shipped with libstdc++ and contains no intrinsics, but three
points needed care; C++26 resolves the first.
\textbf{(i) Two-input shuffles.} The transpose in pass~1 needs zip operations that take lanes from two vectors.
\code{std::experimental::simd} has none; \code{concat} followed by a permute compiled to element-wise moves that cost about three
times the whole pass. We use the compiler's generic vector extension (\code{\_\_builtin\_shufflevector}), which
GCC and clang lower to permute instructions (\code{vpermt2ps} on AVX-512). The re/im swap is written the
same way.
\textbf{(ii) FMA.} libstdc++'s \code{fma(simd,simd,simd)} is not inlined; we write \code{a*b+c} and compile with
\code{-ffp-contract=fast} (GCC's default in GNU mode).
\textbf{(iii) Backends.} vir-simd forwards to libstdc++'s implementation when it is available; with libc++ it
falls back to emulating the vector types with arrays, silently (\S\ref{sec:results}). Our header defines
\code{FASTFFT\_NATIVE\_SIMD} so that callers can detect this case.
\textbf{(iv) C++26.} GCC trunk (\TrunkVersion{}) ships C++26 \code{std::simd}~\cite{p1928}. There (i) has a standard
spelling, \code{permute<W>(cat(a,b), f)}, which GCC lowers to the same \code{vpermt2ps}; with \code{-std=c++26} the
header uses it and needs no compiler extension. It also offers \code{vec<complex<T>{}>}, which we tried as well
(\S\ref{sec:results}).

\section{Method}\label{sec:method}
\code{fftbench} times \code{fastfft}, \code{SimdFFT} (gr4 rev.~\code{af62235}) and FFTW~3.3.10~\cite{fftw}
(built from source with the host's SIMD codelets, \code{FFTW\_MEASURE}) on the same input, uniform random in
$[-1,1)^2$. A \emph{sample} transforms $\max(N,2^{16})$ consecutive values as frames of $N$, the way a streaming gr4
block sees them, repeated until it lasts at least \SI{5}{ms}; one warm-up sample is discarded. Before timing, every
output is checked against a long-double reference DFT. Each process runs 40 rounds; in every round each
implementation is sampled once in a freshly randomised order, so drifts affect all of them alike and same-round
samples can be paired. The process is run three times and pinned to one core. We report the median of the 120
samples per cell with a 95\,\% percentile-bootstrap confidence interval, and speedups as the median of paired
per-round ratios, also with a bootstrap CI~\cite{efron,hoefler}. All values, raw samples and host data are in the
repository; one script (\code{bench/run.sh}) repeats the whole procedure.

Host: virtual machine with \HostCores{} of an Intel Xeon at \SI{2.1}{GHz} nominal (AVX-512 incl.\ FP16, \SI{2}{MiB}
L2 per core), Linux~\HostKernel{}, \HostCompiler{}, \code{-O3 -march=native}. The largest relative median absolute
deviation over all cells was \WorstMAD{}.

\paragraph{Kernel.} Figure~\ref{fig:speedup} summarises the comparison. In single precision \code{fastfft} is
2.5--3.4$\times$ faster than \code{SimdFFT} up to $2^{15}$ and 1.6--2.1$\times$ above, where both are increasingly
bound by memory traffic. Against FFTW the picture depends on $N$ (\FloatVsFftwRange{}): \code{fastfft} is ahead at
$2^6$--$2^{10}$, $2^{13}$--$2^{15}$ and $2^{19}$--$2^{20}$, within 5\,\% at $2^{16}$--$2^{17}$, and behind at
$2^{11}$--$2^{12}$ and $2^{18}$. In double precision the gain over \code{SimdFFT} is
\DoubleVsGrRange{}, smaller because four doubles already fill half an AVX-512 register; \code{fastfft} beats FFTW up
to $2^9$ and at $2^{14}$ and $2^{19}$, is level at $2^{13}$, and FFTW is faster at $2^{10}$--$2^{12}$, $2^{15}$--$2^{18}$ (down to
0.70$\times$) and $2^{20}$. Accuracy is unaffected: the largest error relative to
$\max|X|$ was \FloatErr{} (float) and \DoubleErr{} (double), against \FloatErrGr{} and \DoubleErrGr{} for
\code{SimdFFT} (Table~\ref{tab:acc}).

\paragraph{Vector width.} Compiling \code{fastfft} for narrower vectors separates the effect of width from that of
the algorithm (Table~\ref{tab:width}). With \SI{128}{bit} vectors, the width \code{SimdFFT} uses for floats,
\code{fastfft} is \WidthSixteenVsGr{} as fast as \code{SimdFFT}: the larger radices help mainly for small $N$.
Going from \SI{128}{bit} to \SI{512}{bit} vectors then adds another factor of \WidthGain{}.

\paragraph{C++26 \texttt{std::simd}.} Built with GCC trunk, the extension-free C++26 path is \FloatCxxSmall{}$\times$
slower than the same compiler's \code{<experimental/simd>} path for $N\le 2^9$ (double \DoubleCxxSmall{}$\times$) and
mostly level above, apart from $2^{20}$ (Tables~\ref{tab:gcc17-float},~\ref{tab:gcc17-double}; separate processes,
so not paired). Against \code{SimdFFT} built with the same compiler it remains \FloatTrunkVsGr{}$\times$ faster
(double \DoubleTrunkVsGr{}$\times$).
We also rewrote the kernel on \code{std::simd::vec<std::complex<T>{}>} (\code{fastfft::cx},
\code{include/fastfft/fft\_cx.hpp}). Products and $\pm i$ rotations become plain complex arithmetic, and the twiddle
tables halve. Three things in the current implementation got in the way:
\code{permute} does not accept complex vectors, so the zips go through \code{real()}/\code{imag()} and back;
broadcasting a complex scalar compiles to scalar stores, so we build it from two real broadcasts; and
\code{operator*} carries the Annex~G NaN/Inf recovery unless compiled with \code{-fcx-limited-range}. Accuracy is
unchanged (\CxErr{}). \code{fastfft::cx} is \FloatCxSmall{}$\times$ slower up to $2^{15}$ but takes \FloatCxLarge{}$\times$
the time of the real-lane version from $2^{16}$ (double: \DoubleCxSmall{} and \DoubleCxLarge{}), where the smaller
twiddle tables likely help. Replacing the zip and broadcast workarounds by a non-portable \code{bit\_cast} to a real
vector reduces the small-size gap to \FloatCxbcSmall{}$\times$; the remainder is the generic complex product (three
in-lane shuffles where our pre-arranged twiddles need one).

\paragraph{Emulated \texttt{simd}.} Built with clang~20 and libc++, where vir-simd emulates the vector types,
\code{fastfft} becomes \FallbackSlowdown{} slower and \code{SimdFFT} \FallbackSlowdownGr{} slower
(Table~\ref{tab:libcxx}). Under emulation \code{fastfft} is \emph{slower} than \code{SimdFFT} for $N\ge 2^7$, as its
single-instruction shuffles become element loops, so the patch below enables it only with native types.

\paragraph{In gr4.} The patch (\code{gr4/0001-fastfft.patch}) adds the header to gr4 and makes
\code{gr::algorithm::FFT} use it for complex power-of-two sizes $\ge 64$; real-input and non-power-of-two
transforms still use \code{SimdFFT}. The spectrum block also reuses its output buffer and fuses magnitude, phase and
fftshift into one pass. gr4's FFT unit tests pass
unchanged (GCC~14.2). Measured with gr4's own benchmark facility (Table~\ref{tab:gr4}, 5 alternating runs per
build), the streaming block \code{FFT<T>} gets \GrStreamFloat{} faster for floats and \GrStreamDouble{} for
doubles. The spectrum block \code{FFT<T,DataSet<P>>} (\code{bm\_fft\_block}, $N=1024$) is unchanged within noise
for complex float and real input (\GrSpectrumComplex{}, \GrSpectrumReal{}); the 1.55$\times$ for complex double we
have not analysed. For complex float input it spends about \SI{70}{\micro s} per frame, of which the FFT takes
\SI{0.7}{\micro s}; the rest goes to \code{hypot}, \code{atan2} and building the \code{DataSet}.

\section{Discussion}
Using the native vector width and fewer, larger radix passes is enough to make a portable FFT competitive with a
hand-tuned library on the measured host; nothing in the kernel is specific to x86. FFTW's remaining lead at some
sizes suggests that choosing radices per size, as FFTW's planner does, would help further. With C++26
\code{std::simd} the kernel is pure standard C++, at a cost of 5--25\,\% for small $N$ on today's trunk;
\code{vec<complex<T>{}>} reads most naturally and is already faster for large $N$, and would be for all $N$ once
\code{permute}, broadcast and the complex product are optimised for it. The emulation result shows the other side of portability: code written for native vector types
can become slower than simpler code when the types are emulated, so a library should check which backend it got.

These results come from one virtual AVX-512 core; other CPUs and compilers may differ, and collecting their data
takes one command (\code{bench/run.sh}).
