\begin{abstract}
\noindent GNU Radio~4 computes FFTs with \code{SimdFFT}, a port of PFFFT whose vectors are fixed at four lanes. We
present \code{fastfft}, a single-header Stockham FFT written against \code{std::simd} that uses the full vector width
of the target and contains no intrinsics. On two AVX-512 machines it is \BothFloatVsGr{} faster than \code{SimdFFT}
for complex floats and roughly on par with FFTW. With C++26 \code{std::simd} in GCC trunk it is pure standard C++.
Code, data and the measurement harness are public.
\end{abstract}

\section{Introduction}
GNU Radio~4 (gr4)~\cite{gr4} is a header-only C++23 rewrite of the GNU Radio framework. Its FFTs go through
\code{SimdFFT}, a port of PFFFT~\cite{pffft} to \code{std::experimental::simd}~\cite{ts} via vir-simd~\cite{vir}, which
always uses vectors of four elements. On an AVX-512 machine that leaves three quarters of each register unused for
floats. We asked how fast an FFT can be when written only against the native vector type, so that the width follows
the target, and whether it can keep up with a tuned library.

\section{Algorithm}\label{sec:alg}
\code{fastfft} is a Stockham autosort FFT~\cite{stockham,vanloan}: each pass reads one buffer and writes the other in
natural order, so no bit-reversal is needed. It has three kinds of passes. The first, radix~8, works on several
butterflies at once and transposes their results in registers before storing them. The middle passes, radix~16, work
on independent sub-transforms that share a twiddle factor, so the twiddle is a single broadcast. A final radix~2, 4
or~8 pass handles what remains. Large radices mean few passes over memory: six instead of ten for a million points.
Twiddle tables are laid out so that a complex product costs one multiply, one fused multiply-add and one in-register
swap.

\section{What \texttt{std::simd} could not express}\label{sec:simd}
\code{std::experimental::simd} has no operation that takes lanes from two vectors, which the transpose in the first
pass needs; we use the compiler's generic vector extension there, still without intrinsics. Its \code{fma} is not
inlined, so we write \code{a*b+c} and let the compiler contract it. With libc++, vir-simd silently emulates the vectors
with arrays; the header reports this through \code{FASTFFT\_NATIVE\_SIMD}. C++26 \code{std::simd}~\cite{p1928}, as
implemented in GCC trunk, has the missing two-input permute, so with \code{-std=c++26} the header is pure standard C++.
It also offers vectors of complex numbers, which we tried as well.

\section{Method}\label{sec:method}
A benchmark program checks every implementation against a long-double reference DFT and then times it on a stream of
frames, the way a gr4 block sees data. Each process measures all implementations in 40 rounds, in a new random order
each round, pinned to one core; we run three processes. We report medians with 95\,\% bootstrap confidence intervals,
and speedups as medians of ratios taken within the same round~\cite{efron,hoefler}. Competitors are \code{SimdFFT} and
FFTW~3.3.10~\cite{fftw} built with AVX-512 support. Two hosts were measured: a virtual machine on an Intel Xeon
(GCC~14.2) and a laptop with an \TwoCPU{} (Zen~5, \TwoCompiler{}), both with AVX-512 and both also with GCC
trunk. The spread was small (relative median absolute deviation at most \WorstMAD{}).

\paragraph{Kernel.} \code{fastfft} is faster than \code{SimdFFT} at every size on both hosts
(Figure~\ref{fig:speedup}): \FloatVsGrRange{} for floats on the VM and \TwoFloatVsGr{} on the laptop. The gain is
largest for small and medium sizes and shrinks for large ones, where memory traffic dominates, and in double
precision, where four lanes already fill half of a 512-bit register. Against FFTW the lead changes hands with size and
precision (\BothFloatVsFftw{} for floats, \BothDoubleVsFftw{} for doubles); for floats \code{fastfft} wins most sizes
from $2^{13}$ up. Accuracy matches both (Table~\ref{tab:acc}).

\paragraph{Vector width.} Compiled for 128-bit vectors, the width \code{SimdFFT} uses, \code{fastfft} is at most
moderately faster than \code{SimdFFT}, and on the laptop slower for large sizes; going to 512 bits adds a factor of up
to three (Table~\ref{tab:width}). Most of the gain
therefore comes from using the full register.

\paragraph{C++26 \texttt{std::simd}.} On the laptop the standard-only C++26 version is as fast as the one built on
\code{<experimental/simd>}; on the VM it is up to a quarter slower for small sizes. Rewriting the kernel on vectors of
\code{std::complex} (\code{fft\_cx.hpp}) gives the most readable code and halves the twiddle tables, which makes it
5--15\,\% faster for the largest sizes. For small sizes it is up to 50\,\% slower, because the current library cannot
permute complex vectors, compiles a complex broadcast to scalar stores, and uses a generic complex product with extra
shuffles. Working around the first two with a non-portable cast recovers most of the gap
(Tables~\ref{tab:gcc17-float}--\ref{tab:gcc17-double}, \ref{tab:two-float}--\ref{tab:two-double}).

\paragraph{Emulated \texttt{simd}.} With clang and libc++, where the vectors are emulated, \code{fastfft} becomes several
times slower, \code{SimdFFT} up to twice, and \code{fastfft} falls behind \code{SimdFFT}, because its shuffles turn into element loops
(Table~\ref{tab:libcxx}). The gr4 patch therefore enables \code{fastfft} only with native vector types.

\paragraph{In gr4.} A small patch routes gr4's complex power-of-two FFTs to \code{fastfft} and streamlines the spectrum
block. gr4's unit tests pass, and its streaming FFT block becomes \GrStreamFloat{} faster for floats
(Table~\ref{tab:gr4}). The spectrum block hardly changes: the FFT takes about 1\,\% of its time, the rest goes to
magnitude, phase and building the output.

\section{Discussion}
Using the native vector width and fewer, larger passes is enough for a portable FFT to keep up with a hand-tuned
library on both hosts, and nothing in the kernel is specific to x86. Choosing radices per size, as FFTW's planner
does, would likely help further. C++26 \code{std::simd} makes the kernel pure standard C++, and vectors of complex
numbers would be its natural formulation once permute, broadcast and the complex product are optimised for them.
Emulation shows the other side of portability: code written for native vectors can be slower than simpler code when
the vectors are emulated, so a library should check which backend it got.
